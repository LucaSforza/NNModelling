# Remote training backend and training configuration

**Status:** Implemented initial version; future work is listed at the end
**Issue:** [#14](https://github.com/LucaSforza/NNModelling/issues/14)
**Updated:** 2026-07-17

## Scope delivered

The initial implementation adds a complete training path from the visual
editor to a backend job:

```text
Svelte diagram
    ↓ NNTree compilation
TrainingSidebar.svelte
    ↓ one JSON document
FastAPI + Valkey
    ↓ priority queue and executor selection
LocalExecutor or SlurmExecutor
    ↓
Hydra/Lightning training artifacts
```

The backend is optional. The existing conversion and command-line training
workflow remains available.

## Job contract

`POST /jobs` receives one versioned JSON document containing the compiled
network, all training configuration, resources, and priority:

```json
{
  "schema_version": 1,
  "network": {"format": "nntree", "value": {}},
  "training": {
    "seed": 42,
    "dataset": {
      "_target_": "dataset.mnist.MNISTDataset",
      "batch_size": 32,
      "num_workers": 4,
      "train_size": 0.8
    },
    "optimizer": {"_target_": "torch.optim.Adam", "lr": 0.001},
    "trainer": {"max_epochs": 20, "accelerator": "auto"},
    "wandb": {"project": "NeuralNetworks", "mode": "online"},
    "early_stopping": {"patience": 3, "min_delta": 0.0},
    "overrides": ["trainer.max_epochs=10"]
  },
  "resources": {
    "cpu": 8,
    "memory_gb": 32,
    "gpu": 1,
    "gpu_memory_gb": 16,
    "gpu_type": "A100",
    "node": null
  },
  "priority": 50
}
```

Dataset targets are Python import paths. The API accepts either the string
shorthand or Hydra's `_target_` mapping. Hydra overrides are applied through
OmegaConf/Hydra and never become shell commands.

## Backend components implemented

### FastAPI

The backend is in `converted/src/backend/` and exposes:

```text
GET    /health
GET    /datasets
GET    /compute-units
POST   /jobs
GET    /jobs
GET    /jobs/{job_id}
GET    /jobs/{job_id}/logs
GET    /jobs/{job_id}/events
DELETE /jobs/{job_id}
```

`/datasets` discovers dataset classes installed in the backend Python
environment and returns their constructor metadata. No dataset code is
uploaded by the frontend.

### Job lifecycle

The public states are:

```text
queued → running → succeeded
                 ├→ failed
                 └→ cancelled
```

The implementation has no retry, paused, retrying, or lease state. Heartbeats
are timestamps and executor diagnostics. Failed jobs retain their error
summary and captured output.

### Hydra and artifacts

For each job the backend stores the submitted configuration, generated Hydra
groups, resolved configuration, logs, checkpoints, and W&B offline files:

```text
converted/jobs/{job_id}/
├── requested_config.json
├── resolved_config.yaml
├── cfg/
├── stdout.log
├── stderr.log
└── checkpoints/results generated by Lightning
```

The default artifact root is `converted/jobs/`. `NNM_BACKEND_ARTIFACT_ROOT`
can override it for a mounted Docker or shared Slurm filesystem. The artifact
directory is ignored by Git.

### Valkey

Valkey is the persistent control plane. The deployment configuration enables
AOF and periodic RDB snapshots. The current key model is:

```text
job:{id}                  JSON metadata and submitted configuration reference
job:{id}:events           Valkey Stream of lifecycle events
queue:priorities         sorted priority index
queue:priority:{value}   timestamp-sorted FIFO bucket for one priority
```

Queue claiming is atomic through a Valkey Lua operation. The scheduler selects
the highest priority and then the oldest job at that priority. The executor
selector advances through compatible configured compute units round robin.

### Executors and resources

The common executor interface is used by:

- `LocalExecutor`, which launches the repository's fixed `src/main.py`
  entrypoint and captures stdout/stderr;
- `SlurmExecutor`, which creates a validated `batch.sh` and submits it with
  local `sbatch` or `ssh <host> sbatch` using stdin.

Resource requests include CPU, memory, GPU count, GPU memory, GPU type, and an
optional node selector. Arbitrary client commands and arbitrary batch scripts
are not accepted.

The initial scheduler intentionally runs one job at a time. Slurm compute
units are currently configured logical profiles with capacities; the backend
can therefore run on a CPU-only machine or against a Slurm profile without
changing the API.

## Frontend and model loading

`TrainingSidebar.svelte` is a separate mode from the node property sidebar.
It provides:

- dataset selection and discovered constructor parameters;
- optimizer, trainer, early stopping, and W&B fields;
- arbitrary Hydra override lines;
- resource and priority fields;
- job list, live status through SSE, cancellation, and W&B links.

The frontend calls FastAPI directly through the shared REST/SSE API. The MCP
server has an optional thin HTTP proxy for the same job IDs and state; it does
not duplicate the queue.

The `Carica` toolbar action accepts source Svelte Flow JSON with `nodes` and
`edges`. It keeps the file input in the DOM while Chrome's picker is open,
does not replace the diagram on parse failure, and displays a visible error.
Pre-converted files in `examples/nntrees/` are NNTree artifacts and must not be
loaded into the visual editor; use the corresponding source file in
`examples/diagrams/`.

## Tests and verification

The implementation includes:

- frontend unit tests for the editor, type engine, serialization, and training
  integration helpers;
- a source-model integration test controlled by `NNM_MODEL_PATH` that rejects
  converted NNTree paths, runs type checking, and compiles the source diagram;
- backend tests for API validation, dataset discovery, priority/FIFO queueing,
  persistence behavior, local execution, and Slurm script generation;
- MCP proxy unit tests;
- direct Chrome verification of source-model loading and a completed local
  MNIST training job.

Useful commands:

```bash
pnpm --dir front-end test
pnpm --dir front-end check
NNM_MODEL_PATH=examples/diagrams/transformer_classifier.json \
  pnpm --dir front-end test:integration:model
cd converted && PYTHONPATH=src uv run pytest src/tests/test_remote_backend.py -q
```

## Future features

The following are intentionally future features, not part of the initial
implementation:

1. Run multiple compatible jobs concurrently while preserving atomic queue
   claims and round-robin assignment.
2. Model physical Slurm resources explicitly, including a node containing
   multiple individually schedulable GPUs and GPU-memory capabilities.
3. Make input dtype requirements dataset-aware so models such as a Transformer
   with `Embedding` can be checked against the selected dataset's index dtype.
